# ParkGolfFinder 수집 봇 설계 초안

## 목표
- 파크골프 시설 / 예약 정보를 외부 원천에서 수집한다.
- 수집 결과를 바로 본 테이블에 쓰지 않고, **DB staging**을 거쳐 정제한다.
- 저장공간이 부족한 환경을 고려해 **원문 대용량 파일 스냅샷은 기본 저장하지 않는다**.
- 봇은 웹앱과 별개 실행 단위로 두되, **같은 저장소 / 같은 DB**를 공유한다.

## 제품 범위
### 포함
- 외부 원천 수집
- 정규화
- 검수 판정
- staging 적재
- 본 테이블 승격
- staging 정리

### 제외
- 웹 서버
- 사용자 화면
- 예약 대행
- 대량 원문 파일 보관
- 상시 데몬 실행

## 실행 형태
- 봇은 **CLI 워커**다.
- 필요할 때 수동 실행한다.
- 기본적으로 `run` 한 번으로 전체 파이프라인을 돌릴 수 있게 한다.
- 특정 단계만 재실행할 수 있게 한다.

## 파이프라인
### 1) fetch
- 외부 원천을 읽는다.
- 이 단계는 수집만 담당한다.

### 2) stage
- 필요한 텍스트 / URL / 해시 / 추출 필드만 staging 테이블에 넣는다.
- 원문 HTML과 이미지 대량 저장은 하지 않는다.

### 3) normalize
- 주소, 지역, 요금, 예약방식 표기를 정리한다.
- `province`, `district`, `regionKey`를 계산한다.

### 4) review
- 후보 / 확정 / 숨김을 판정한다.
- 기준은 주소 정합성, 운영중 여부, 예약 정보 신뢰도, 중복 여부다.
- 이 단계에서 **파크골프장인지 여부**도 함께 판정한다.

### 5) promote
- 확정된 것만 본 테이블로 반영한다.
- `Facility`, `FacilityPricing`, `ReservationInfo`, `ReservationMethod`로 승격한다.

### 6) cleanup
- 오래된 staging 데이터를 정리한다.
- 저장공간을 아끼기 위해 중간 데이터 보관 기간을 짧게 둔다.

## 실행 단위

## 저장 방식
### 기본 원칙
- 파일 스냅샷은 기본 저장하지 않는다.
- 수집 결과는 DB staging 중심으로 남긴다.
- 본 테이블과 staging은 분리한다.

### staging 역할
- 중간 결과 보관
- 검수
- 재반영
- 실패 시 재실행

## 추천 DB staging 구조
### `staging_runs`
- 실행 단위
- 시작/종료 시각
- 상태
- 범위
- 통계

### `staging_sources`
- 수집 원천 단위
- source name / URL / hash / fetchedAt

### `staging_facility_records`
- 정규화된 시설 후보
- 이름 / 주소 / 지역 / 좌표 / 신뢰도 / 상태

### `staging_reservations`
- 예약 관련 중간 결과
- 방식 / 규칙 / 링크 / 우선순위

### `staging_decisions`
- 확정 / 후보 / 숨김 판정
- 판정 사유
- 검토 시점

### `staging_duplicates`
- 중복 후보 그룹
- 대표 레코드
- 중복 유형
- 중복 사유
- 병합 상태

## 저장공간 제약 대응
- 원문 HTML 전체를 저장하지 않는다.
- 이미지/스크린샷을 기본으로 저장하지 않는다.
- 텍스트 중심 요약만 남긴다.
- 오래된 staging 데이터는 주기적으로 삭제한다.

## 본 테이블과의 관계
- 웹앱은 본 테이블만 읽는다.
- 봇은 staging을 거친 뒤 확정 데이터만 본 테이블에 승격한다.
- 봇이 실패해도 본 서비스 데이터가 바로 망가지지 않도록 분리한다.

## 일반 중복 처리 규칙
중복은 자동 삭제보다 **그룹화와 대표 선택**을 우선한다.

### 1) 원천 내부 중복 제거
- 같은 URL
- 같은 원문 해시
- 같은 이름 + 같은 주소

### 2) 정규화 후 중복 병합
- 시설명 유사
- 주소 정규화 결과 동일
- 운영기관 동일
- 좌표가 거의 동일

### 3) 애매한 경우
- 바로 합치지 않는다.
- `candidate` 또는 `ambiguous`로 두고 보류한다.

### 중복 상태 예시
- `exact`
- `probable`
- `ambiguous`

### 중복 처리 원칙
- 자동 병합은 exact 위주로만 한다.
- probable은 점수 기반으로만 병합 후보를 만든다.
- ambiguous는 자동 삭제하지 않는다.
- 대표 레코드만 본 테이블에 승격하고, 나머지는 추적 정보로 남긴다.

## 파크골프장 판별 규칙
봇은 일반 골프장과 **파크골프장**을 구분해야 한다.

### 포함 기준
- 공식 원천에 `파크골프`, `파크골프장`, `park golf`가 명시된다.
- 시설 설명이나 예약 페이지에서 파크골프 시설임이 분명하다.
- 공공기관/지자체 자료에서 파크골프 시설로 분류된다.

### 제외 기준
- `골프장`, `golf course`, `golf club`만 있고 파크골프 근거가 없다.
- 일반 골프 연습장 / 골프클럽 / 스크린골프 시설이다.
- 파크골프인지 불명확한 경우다.
- 시설명에 `파크`가 들어가더라도 그것만으로는 포함하지 않는다.
- 예: `OO파크골프클럽` 같은 이름은 **공식 설명 / 예약 페이지 / 공공 분류**가 파크골프인지 확인돼야 포함한다.

### 판정 원칙
- 파크골프 근거가 없으면 본 테이블로 승격하지 않는다.
- 애매한 경우는 `candidate` 또는 `hidden`으로 둔다.
- 일반 골프장은 별도 서비스 범위로 취급하지 않는다.
- 이름은 약한 신호일 뿐이며, 최종 판정은 **공식 분류와 설명**을 우선한다.

## 운영 원칙
- 웹앱과 봇은 같은 저장소 안에 둔다.
- 실행은 분리한다.
- DB만 공유한다.
- 봇은 웹앱에 직접 의존하지 않는다.

## 완료 기준
- 봇은 CLI로 실행된다.
- staging을 거친 뒤에만 본 테이블 반영이 가능하다.
- 원문 대용량 파일 저장 없이도 재실행과 검수가 가능하다.
- 웹앱과 봇의 경계가 분명하다.
