# ParkGolfFinder 수집 봇 설계 초안

## 목표
- 파크골프 시설 / 예약 정보를 외부 원천에서 수집한다.
- 수집 결과를 바로 본 테이블에 쓰지 않고, **DB staging**을 거쳐 정제한다.
- 저장공간이 부족한 환경을 고려해 **원문 대용량 파일 스냅샷은 기본 저장하지 않는다**.
- 봇은 웹앱과 별개 실행 단위로 두되, **같은 저장소 / 같은 DB**를 공유한다.

## 제품 범위
### 포함
- 외부 원천 수집
- 정규화
- 검수 판정
- staging 적재
- 본 테이블 승격
- staging 정리

### 제외
- 웹 서버
- 사용자 화면
- 예약 대행
- 대량 원문 파일 보관
- 상시 데몬 실행

## 실행 형태
- 봇은 **CLI 워커**다.
- 필요할 때 수동 실행한다.
- 기본적으로 `run` 한 번으로 전체 파이프라인을 돌릴 수 있게 한다.
- 특정 단계만 재실행할 수 있게 한다.

## 파이프라인
### 1) fetch
- 외부 원천을 읽는다.
- 이 단계는 수집만 담당한다.

### 2) stage
- 필요한 텍스트 / URL / 해시 / 추출 필드만 staging 테이블에 넣는다.
- 원문 HTML과 이미지 대량 저장은 하지 않는다.

### 3) normalize
- 주소, 지역, 요금, 예약방식 표기를 정리한다.
- `province`, `district`, `regionKey`를 계산한다.

### 4) review
- 후보 / 확정 / 숨김을 판정한다.
- 기준은 주소 정합성, 운영중 여부, 예약 정보 신뢰도, 중복 여부다.

### 5) promote
- 확정된 것만 본 테이블로 반영한다.
- `Facility`, `FacilityPricing`, `ReservationInfo`, `ReservationMethod`로 승격한다.

### 6) cleanup
- 오래된 staging 데이터를 정리한다.
- 저장공간을 아끼기 위해 중간 데이터 보관 기간을 짧게 둔다.

## 실행 단위
- 전체 재수집
- 광역권역별 재수집
- 원천별 재수집
- 최근 변경분 재반영

## 저장 방식
### 기본 원칙
- 파일 스냅샷은 기본 저장하지 않는다.
- 수집 결과는 DB staging 중심으로 남긴다.
- 본 테이블과 staging은 분리한다.

### staging 역할
- 중간 결과 보관
- 검수
- 재반영
- 실패 시 재실행

## 추천 DB staging 구조
### `staging_runs`
- 실행 단위
- 시작/종료 시각
- 상태
- 범위
- 통계

### `staging_sources`
- 수집 원천 단위
- source name / URL / hash / fetchedAt

### `staging_facility_records`
- 정규화된 시설 후보
- 이름 / 주소 / 지역 / 좌표 / 신뢰도 / 상태

### `staging_reservations`
- 예약 관련 중간 결과
- 방식 / 규칙 / 링크 / 우선순위

### `staging_decisions`
- 확정 / 후보 / 숨김 판정
- 판정 사유
- 검토 시점

## 저장공간 제약 대응
- 원문 HTML 전체를 저장하지 않는다.
- 이미지/스크린샷을 기본으로 저장하지 않는다.
- 텍스트 중심 요약만 남긴다.
- 오래된 staging 데이터는 주기적으로 삭제한다.

## 본 테이블과의 관계
- 웹앱은 본 테이블만 읽는다.
- 봇은 staging을 거친 뒤 확정 데이터만 본 테이블에 승격한다.
- 봇이 실패해도 본 서비스 데이터가 바로 망가지지 않도록 분리한다.

## 운영 원칙
- 웹앱과 봇은 같은 저장소 안에 둔다.
- 실행은 분리한다.
- DB만 공유한다.
- 봇은 웹앱에 직접 의존하지 않는다.

## 폴더 구조 초안
```txt
/
├─ apps/
│  ├─ web/
│  └─ bot/
├─ packages/
│  ├─ db/
│  └─ shared/
└─ docs/
```

## 완료 기준
- 봇은 CLI로 실행된다.
- staging을 거친 뒤에만 본 테이블 반영이 가능하다.
- 원문 대용량 파일 저장 없이도 재실행과 검수가 가능하다.
- 웹앱과 봇의 경계가 분명하다.
